# MariaDB 10.11 on Ubuntu 24.04: compatibility and what it offers the jury tool

Branch `ukwikidev/mariadb-10.11` (from `codex/deployment-procedure`). The VPS moves from Ubuntu 22.04 (MariaDB 10.6.22) to Ubuntu 24.04, whose package is **MariaDB 10.11.14** (`1:10.11.14-0ubuntu0.24.04.1`). This note covers what changes, what the branch does about it, and which 10.7–10.11 features help this code.

## Summary

- **Compatible as is.** The full test suite passes on 10.11.14 (444 tests, 0 failures), and so do the deployment tests on an Ubuntu 24.04 image with the real release ZIP (81 tests; MariaDB 10.11.14, Python 3.12). No query, migration or config needed a change to run on 10.11.
- **One feature is worth using now: descending index keys (10.8).** The juror gallery orders by `rate DESC, monument_id ASC, page_id ASC`; on 10.6 no index can give that order, so every page sorted all the juror's rows. V61 stores `rate` descending in the gallery index. Performance: see [Benchmarks](#benchmarks).
- **The rest of 10.7–10.11 doesn't apply to this code** (new types, JSON functions, replication and privilege features), or helps operations rather than code (`SHOW ANALYZE`, dynamic redo log size).
- **Two traps:** Flyway can't be upgraded to the release that knows 10.11 (it drops the B44 baseline), and V61 must not run on 10.6 (it would silently build an ascending index), so it refuses to.

Flyway stays at **9.16.3**. On 10.11 it logs `Flyway upgrade recommended: MariaDB 10.11 is newer than this version of Flyway ... latest supported 10.10`, a warning only. 9.22.3 (the 9.x release that knows 10.11) no longer applies `B44__Baseline.sql` to an empty database: it replays V1 onwards and fails at V51 (`Can't DROP INDEX monument_id_index`). Seen both in the test suite and with the `flyway/flyway:9.22.3` CLI. Upgrading Flyway means replacing the B44 baseline approach first.

## Defaults that changed (10.6.22 → 10.11.14)

From `mariadbd --no-defaults --verbose --help` on both bench images (path, host and id variables left out):

| Variable | 10.6.22 | 10.11.14 | Effect here |
|---|---|---|---|
| `explicit_defaults_for_timestamp` | OFF | **ON** (10.10) | A TIMESTAMP column without explicit `NULL`/`DEFAULT` is now nullable, default NULL, no auto-update. Every TIMESTAMP in B44 and V60 states both, and a dump states them too, so the schema is identical. **New migrations must keep stating them.** |
| `optimizer_prune_level` | 1 | **2** (+ `optimizer_extra_pruning_depth` = 8) | More aggressive join-order pruning for many-table joins. Our queries join at most three tables; no plan change expected. The benchmark checks it. |
| `innodb_prefix_index_cluster_optimization` | OFF | ON | Avoids clustered-index lookups for prefix-index reads; we have no prefix indexes on hot paths. |
| `innodb_log_write_ahead_size` | 8192 | 512 | Part of the 10.8 redo log rewrite (below). |
| `innodb_buffer_pool_chunk_size` | 128M | 0 (auto) | Buffer pool resizing granularity; with 256M no difference. |
| New: `innodb_buffer_pool_size_max`, `innodb_buffer_pool_size_auto_min` | – | 0 | Buffer pool resizing / shrinking under memory pressure. Inactive at these values; worth a look for the shared VPS, not needed. |
| New: `innodb_alter_copy_bulk` | – | ON | `ALTER ... ALGORITHM=COPY` builds the new table in bulk. Would have sped up V55.1's InnoDB conversion; that runs on the old server, before the move. |
| New: `innodb_log_file_mmap`, `innodb_linux_aio` | – | ON, auto | Redo log via mmap; io_uring or libaio chosen automatically. |
| New: `log_slow_query`, `log_slow_query_time`, `log_slow_query_file` | – | aliases | New names for `slow_query_log`, `long_query_time`, `slow_query_log_file`. Production's `slow-log.cnf` keeps working with the old names. |

Unchanged: `optimizer_switch` (the same flags in both), `histogram_type` (`DOUBLE_PREC_HB`; JSON histograms exist since 10.8 but aren't the default), `use_stat_tables`, `optimizer_use_condition_selectivity` = 4, `innodb_flush_method` = O_DIRECT, `innodb_log_file_size` = 96M, change buffering off. Ubuntu's `/etc/mysql` files in 24.04 differ from 22.04's only in the `[mariadb-10.11]` section name (production's copies also lack `bind-address = 127.0.0.1`).

The cost-based optimizer is the same generation as 10.6: the rewritten cost model is MariaDB 11.0. So 10.6 → 10.11 carries little risk of plans changing; a later move to 11.4 would be the one to benchmark plan by plan.

## Features of 10.7–10.11, checked against this code

| Feature (version) | Where it could apply | Decision |
|---|---|---|
| **Descending index keys (10.8)** | Juror gallery: `ORDER BY rate DESC, s.monument_id ASC, s.page_id ASC` (`GalleryService`), over `(jury_id, round_id, rate, monument_id, page_id)` (V48) | **Done: V61.** See below. |
| Descending keys elsewhere | Other descending orders: `ImageJdbc` grouped list and `RoundDistributionHandler` top-N order by aggregates (`SUM(rate)`), which no index can provide; `SelectionJdbc`'s `rate -> -1` is a single-direction order, which an ascending index already serves backwards | None. |
| `UUID` type (10.7) | `rounds.submit_token VARCHAR(36)` (V59) | No: one value per round, a few hundred rows. 20 bytes per row saved, a migration spent. |
| `INET4`/`INET6` (10.10/10.5) | — | Nothing stores addresses. |
| `JSON_OVERLAPS`, `JSON_EQUALS`, `JSON_NORMALIZE`, JSONPath ranges (10.7/10.9) | `job.params`/`job.state` (JSON) | No: always read whole and parsed in Scala; no query looks inside them. |
| `NATURAL_SORT_KEY()` (10.7) | Region / monument id ordering | No: monument ids are fixed-width (`05-104-0001`); regions are sorted in Scala. |
| `SFORMAT()`, `RANDOM_BYTES()` (10.7/10.10) | — | Nothing to replace. |
| JSON histograms, `histogram_type=JSON_HB` (10.8) | Selectivity of skewed columns (`rate`) | Not needed: the plans on the hot queries are already right. Would need `ANALYZE TABLE ... PERSISTENT FOR ALL`, which no migration runs. |
| `SHOW ANALYZE [FORMAT=JSON] FOR <connection>` (10.9) | Diagnosing a slow query while it runs on production | **Operations:** useful next to the slow log; no code change. |
| Redo log rewrite (10.8), dynamic `innodb_log_file_size` (10.9) | Write bursts of round distribution and voting | Free with the upgrade; the redo size can now be tuned without a restart. Measured in the benchmark (distribution jobs). |
| Lag-free `ALTER` for replication (`binlog_alter_two_phase`, 10.8) | — | No replication. |
| `GRANT ... TO PUBLIC` (10.11), password reuse check (10.7) | — | One application account. |
| `explicit_defaults_for_timestamp=ON` (10.10) | Future migrations | Keep writing `NULL`/`NOT NULL` and `DEFAULT` on every TIMESTAMP. |

## V61: the gallery index with `rate` descending

**Before.** V48 created `(jury_id, round_id, rate, monument_id, page_id)` for the gallery, but on 10.6 a mixed-direction `ORDER BY` can't be read from an ascending index, and 10.6 parses `DESC` in an index definition and ignores it. Each gallery page sorted all of the juror's rows of the round (~19k on the Gatling fixture). The deferred join (`ImageDbNew.deferredJoinPage`, commit 617dc75) limits that sort to narrow index entries (127 ms → 13 ms on the fixture), but the sort remains.

**V61.** `ALTER TABLE selection ADD INDEX idx_selection_jury_round_ratedesc_mon_page (jury_id, round_id, rate DESC, monument_id, page_id), DROP INDEX idx_selection_jury_round_rate_mon_page, ALGORITHM = INPLACE, LOCK = NONE`. The index has the same columns, so the gallery, its count, the region filter and the jurors' rate stats keep their access paths; only the order of `rate` within a juror's round flips. The page is then read from the index in order: with `LIMIT 15 OFFSET n` it reads n + 15 index entries instead of sorting the whole round. No query changes: the deferred join stays, because deep pages still read n entries, which is far cheaper index-only than with a full-row lookup for each.

**Guard.** On a server before 10.8, V61 stops with `V61 needs MariaDB 10.8 or later for descending index keys` before any DDL. Checked with the real ZIP on the 22.04 / 10.6.23 image. Without the guard, 10.6 would create the index ascending without a word, and a dump of it would carry the ascending index to 10.11, where Flyway would never run V61 again.

**Tests.** `SelectionGalleryIndexSpec` checks the index's column order and directions (`information_schema.STATISTICS.COLLATION` = `D` for `rate`), and that a gallery page over it needs no filesort and comes back in the gallery's order.

## Moving production

1. Deploy the current release (V60) on the old server as planned (`docs/deployment.md`); V55.1's InnoDB conversion happens there.
2. Build the 24.04 server (`wlxjury-infra`, which still targets 22.04: `tests/Dockerfile`, the README, the inventory comment). MariaDB settings as now: the package files, the slow log, `innodb_buffer_pool_size = 256M`.
3. Move the database with `mariadb-dump --databases wlxjury` from 10.6 and restore it into 10.11. A dump of the application database only needs no `mariadb-upgrade`; the accounts come from the playbook. (An in-place datadir upgrade also works after a clean shutdown: the bench does exactly that, with `mariadb-upgrade`.)
4. Only then deploy this branch: V61 runs on 10.11 (online; on production's 3M selection rows it builds one secondary index, measured in the benchmark's startup).

**Do not deploy this branch to the 22.04 server:** startup stops at V61, leaving a failed V61 row in `flyway_schema_history` that needs `flyway repair` (or the release tool's restore) before the old release starts again.
