# MariaDB 10.11 on Ubuntu 24.04: compatibility and what it offers the jury tool

Branch `ukwikidev/mariadb-10.11` (from `codex/deployment-procedure`). The VPS moves from Ubuntu 22.04 (MariaDB 10.6.22) to Ubuntu 24.04, whose package is **MariaDB 10.11.14** (`1:10.11.14-0ubuntu0.24.04.1`). This note covers what changes, what the branch does about it, and which 10.7–10.11 features help this code.

### V85 on 10.6 and on 10.8+

**On MariaDB 10.8+ (10.11)**, V85 runs one statement, then `ANALYZE TABLE vote`:
`ALTER TABLE vote ADD INDEX IF NOT EXISTS vote_jury_round_ratedesc_mon_page_idx (jury_id, round_id, rate DESC, monument_id, page_id), DROP INDEX IF EXISTS vote_jury_round_rate_mon_page_idx, ALGORITHM = INPLACE, LOCK = NONE`.
It is online; the original measured 10.9 s on 3.07M rows.

V85 acts on what it finds, read from `information_schema.STATISTICS`. Its guard is the startup
check's condition: some gallery index has `rate` ascending.

| State on 10.8+ | V85 runs |
|---|---|
| only the old index (V82's) | the swap above |
| `ratedesc` with `D`, and the old index still there (part-way) | `DROP INDEX vote_jury_round_rate_mon_page_idx` |
| `ratedesc` with `A`, made before 10.8 (e.g. a 10.11 dump restored on 10.6 and moved on again), with or without the old index | one `ALTER`: drop the old index if it's there, drop `ratedesc` and add it again with `rate DESC` (verified on 10.11.14 by the reviewer) |
| `ratedesc` with `D` alone (done), or neither index | nothing (`DO 0`, no notes) |

`ANALYZE TABLE vote` runs only after an `ALTER`. So V85, or a copy of it under a later number
(open question 1), is safe to run anywhere and as often as needed. Running it by hand is the same
as running its `ALTER` for the state found.

**Before 10.8 (production's 10.6)**, the `ALTER` is not run:
- The script raises a warning instead (`SIGNAL SQLSTATE '01000'`). Flyway logs it as `DB: V85: vote gallery index left ascending (needs MariaDB 10.8+); run its ALTER again after the server move`.
- V85 is recorded as applied, and the schema stays as V84 left it.
- The original refused instead. That would stop every followups deploy on 10.6 and leave a failed history row.
- Building the index anyway would be wrong too. 10.6 parses `DESC` and ignores it, so the result would be an ascending index under a descending name, and neither `mariadb-upgrade` nor a dump would ever fix it.

**V85 needs a re-run after the move if it first ran on 10.6**, because Flyway never re-runs an
applied version. The script is safe to run again: where the swap is done it changes nothing, and on
10.6 it changes nothing and warns again. See the pre-deploy items and the runbook
(`docs/deployment.md`, "MariaDB 10.11: V85's gallery index"). If the first release with V85 is
deployed only after the move, V85 does the swap itself and nothing more is needed.

**Backstop.** After migrating (or validating), every start checks the index
(`db.Migrations.galleryIndexLeftAscending`): on a 10.8+ server where `rate` is still ascending
in the gallery index, it logs a WARN naming the runbook section. The check never fails a start;
an error in it is logged as a WARN with the exception's class only.

The version check reads `VERSION()` (`major * 1000 + minor >= 10008`), as the original's did.

**Specs.** `db.VoteGalleryIndexSpec` follows the test server:
- On 10.6: the old index is unchanged, there is no new one, the warning appears, and a gallery page comes back in order (with a filesort).
- On 10.8+: the index is descending, and a page needs no filesort.
- On both: V85 is re-run on a scratch copy of `vote` that has the ascending index, as a production migrated on 10.6 has it after the move.
- On 10.8+ only (skipped on 10.6), the other states are tested: both indexes, with `ratedesc` descending; `ratedesc` ascending with the old index; and `ratedesc` ascending alone. Each must end with one descending index, unflagged by the startup check, with no warnings and no change on a second run. The backstop's check is tested on the same copy, before and after. On 10.8+ a second run leaves no warning or note at all.
- The no-filesort check uses `FORCE INDEX`: on a few test rows the optimizer may prefer a table scan. The check is about what the index can give, not the optimizer's choice on tiny data.

**No benchmark rerun.** P0 renamed the table and the index, and P1 left the juror gallery's
inner query unchanged: `select s.id, … from vote s where jury_id/round_id … order by rate desc,
s.monument_id, s.page_id limit …`. That is the same columns and order as the benchmarked V61. On
10.11 the spec's plan check (no filesort over the new index) confirms the mechanism. A paired
pilot couldn't change the decision.

### `explicit_defaults_for_timestamp`: a migration (V86), not a server setting

A database created fresh on 10.11 differs from a 10.6 one in three columns. The Flyway batch found
the first two (`docs/plans/2026-11-03-flyway.md`, section 4). The port's 10.11.18 run found the
third: `FlywayUpgradeSpec`, a 10.6-built V82 database migrated on 10.11 against a fresh one.

| Column | Created on 10.10+ | Created on 10.6 (production's form; V77 hasn't run there yet) |
|---|---|---|
| `round.created_at` | `timestamp NOT NULL`, no default | `NOT NULL DEFAULT current_timestamp() ON UPDATE current_timestamp()` |
| `users.created_at` | `NULL DEFAULT current_timestamp()` | `NOT NULL DEFAULT current_timestamp()` |
| `account_token.expires_at` (V77) | `timestamp(3) NOT NULL`, no default | `NOT NULL DEFAULT '0000-00-00 00:00:00.000'` |

**Choice: V86 (`V86__Timestamp_defaults_as_on_10_6.sql`).** It gives these columns the 10.6
definitions, but only where a column still has the 10.10+ form: `round.created_at` or
`account_token.expires_at` without a default, or `users.created_at` nullable. The app always
writes the first two, so their defaults only make the schemas the same. Before the change, NULL `users.created_at` rows are set
to now. On a database created on 10.6, every statement is `DO 0` and nothing is rebuilt.
Production's schema doesn't change, whether the move is an in-place upgrade or a dump.

Why a migration rather than `explicit_defaults_for_timestamp=OFF` on the new server and in the
10.11 test container:
- The setting would have to follow every server that creates a database: CI, developers, `docker-compose.test.yml`, a rebuilt VPS and the infra playbook.
- Missing it once brings the difference back silently, and then an `INSERT` into `round` without `created_at` fails in strict mode.
- The migration gives the same schema on every server whatever the setting, and the specs prove it.

The new server can keep MariaDB's default (ON), like every 10.10+ install. New migrations must
keep stating `NULL`/`NOT NULL` and `DEFAULT` on every `TIMESTAMP`; V77's `expires_at` didn't.
`FlywayUpgradeSpec` can't catch a new omission: from V83 on, both of its sides run the new
migration on the same server. The check is `MigrationNamingSpec`, "state a TIMESTAMP column's NULL, or
NOT NULL and DEFAULT, from V85 on". It lints every V file from V85 on, and has a self-test that
compares the exact lines it flags. It allows `TIMESTAMP NULL` without a DEFAULT, which gives
NULL DEFAULT NULL on every server, and it ignores `CAST(… AS TIMESTAMP)`. The older
files are history. V86 fixes the three columns that mattered; the others, such as V2's and V3's
`deleted_at TIMESTAMP NULL`, come out the same on both servers.

V86's zero default for `account_token.expires_at` is refused where `sql_mode` has `NO_ZERO_DATE`
with strict mode. Neither production's 10.6 nor Ubuntu's 10.11 has that by default, and V77
itself would fail the same way. Record `@@sql_mode` in the rehearsal (pre-deploy item 4).

`db.TimestampDefaultsMigrationSpec` builds both forms in scratch databases with the session
variable, so it runs on 10.6 and 10.11 alike. It checks that:
- the test database has the 10.6 definitions;
- a database made on 10.10+ gets them and keeps its rows;
- a second run changes nothing;
- a database made on 10.6 is untouched, its `SHOW CREATE TABLE` included.

Production's `users.created_at` also has `ON UPDATE current_timestamp()`, from an older schema
(`test/resources/db/prod-v53-myisam-schema.sql`); a fresh database lacks it. V86 leaves it alone
(open question 3).

The reviewer noted that production already differs from a fresh database elsewhere too:
- `users.created_at` and `user_contest.created_at` have `ON UPDATE`;
- `comment.created_at` is `TEXT`;
- there is a legacy `selection_backup` table.

V86 doesn't aim to remove these. It makes a database created on 10.11 equal to one created on
10.6 by the same migrations; production's own history is a separate matter.

### Pre-deploy items for the server move

1. **Order.** Deploy releases from followups on 10.6 as usual. There V85 is a no-op with its warning, and V86 is a no-op. Nothing in this branch requires the move first.
2. **Move the database** as in [Moving production](#moving-production), step 3: `mariadb-dump --databases wlxjury` from 10.6 restored into 10.11, or an in-place upgrade with `mariadb-upgrade`. Both keep production's column and index definitions.
3. **Re-run V85 once on 10.11** if `flyway_schema_history` has version 85 from 10.6. The check query (`TABLE_SCHEMA = DATABASE()`, in the `WLXJURY_DB` database) and the statements are in `docs/deployment.md`, "MariaDB 10.11: V85's gallery index". The app's start WARN is the backstop.
   - It is online and took about 11 s on 3M rows; measure it on the rehearsal copy.
   - **Repeat the check after any restore on 10.11.** A backup taken before the re-run brings back the ascending index.
   - Instead of the manual step, the first release after the move could carry a copy of V85 under a new number (open question 1).
4. **`explicit_defaults_for_timestamp`: nothing to set.** For the record, run `SELECT @@version, @@explicit_defaults_for_timestamp, @@sql_mode` on the new server. `NO_ZERO_DATE` with strict mode would refuse V86's (and V77's) zero default on a fresh database. V86 keeps a freshly created database (staging, a rebuilt server) the same as production's schema.
5. **Switch the defaults with the move, in one commit.** The original branch had these switches:
   - `SharedTestDb.Image` → `mariadb:10.11.14`, Ubuntu 24.04's build (`1:10.11.14-0ubuntu0.24.04.1` in noble-updates on 2026-11-03); the Gatling fixture follows it;
   - `Dockerfile.test`'s default → `UBUNTU=24.04`;
   - `docker-compose.test.yml`;
   - `run-with-prod-dump.sh` (a 10.11 client, `mariadb-dump`);
   - the bench's `bench/server/Dockerfile` (the 24.04 image is `Dockerfile.noble` until then).
6. **Deployment tests on the 24.04 image**, with the real ZIP: `docker build --build-arg UBUNTU=24.04 -f scripts/deployment/Dockerfile.test …`. Run in the port after the review fixes (24 OK, above); rerun with the release built for the move.
7. **Rehearse the move** on an isolated production copy:
   - the dump and restore, or the in-place upgrade;
   - the release's start;
   - the V85 re-run and its time;
   - a gallery page's plan (`EXPLAIN` without a filesort);
   - backup and restore with the 10.11 tools.
8. **Infra.** `wlxjury-infra` (postponed by the user) still targets 22.04; this port doesn't touch it.

### Open questions for the user

1. **[open: user] How V85's re-run happens after the move.** The options:
   - (a) by hand, from the runbook (item 3). This port implements it as documentation only.
   - (b) a copy of V85 under the next free number, in the first release built after the move. It gets reviewed, recorded in the history and run automatically. It must not be added while production is on 10.6, where it would be a no-op again.
   - (c) a gate: keep V85 out of followups until the move, so it only ever runs on 10.11.

   Recommended: (b) if the move is more than one release away, otherwise (a). Reviewer: (b), a guarded copy under a new number, added only in a release built after the move. V85's guard makes the copy a no-op wherever the swap is done.
2. **[open: user] The test default after the move.** Either Ubuntu's `mariadb:10.11.14` (production's build) or the current upstream patch (`10.11.18` was the newest image older than two weeks on 2026-11-03). Recommended: 10.11.14, production's build. Reviewer: 10.11.14, keeping a 10.6 lane (`-Dwlxjury.test.mariadb-image=mariadb:10.6.22`) until the move is complete.
3. **[open: user] `round.created_at` updates itself.** On 10.6, and so on production, `round.created_at` has `ON UPDATE current_timestamp()`; production's `users.created_at` has it too. So every update of a round or user row resets its "created" time. V86 keeps the 10.6 definitions so that the schema is the same everywhere. Dropping the `ON UPDATE` from both would take one metadata-only migration, but it changes behaviour: the app reads `Round.createdAt`. Recommended: a separate small migration, if the dates matter. Reviewer: a separate small `ALGORITHM=INSTANT` migration later, if the dates are wanted.

## Summary

- **Compatible as is.** The full test suite passes on 10.11.14 (444 tests, 0 failures), and so do the deployment tests on an Ubuntu 24.04 image with the real release ZIP (81 tests; MariaDB 10.11.14, Python 3.12). No query, migration or config needed a change to run on 10.11.
- **One feature is worth using now: descending index keys (10.8).** The juror gallery orders by `rate DESC, monument_id ASC, page_id ASC`; on 10.6 no index can give that order, so every page sorted all the juror's rows. V61 stores `rate` descending in the gallery index. On the production snapshot it cuts the region gallery's buffer-pool reads by 35% (p95 31 → 23 ms) and the juror gallery's by 20%, at no measurable cost to voting or distribution; see [Benchmarks](#benchmarks).
- **No performance regression from 10.6.22 to 10.11.14** in the production-like benchmark (same app, back to back, drift checked with a repeat run).
- **The rest of 10.7–10.11 doesn't apply to this code** (new types, JSON functions, replication and privilege features), or helps operations rather than code (`SHOW ANALYZE`, dynamic redo log size).
- **Two traps:** Flyway can't be upgraded to the release that knows 10.11 (it drops the B44 baseline), and V61 must not run on 10.6 (it would silently build an ascending index), so it refuses to.

## Defaults that changed (10.6.22 → 10.11.14)

From `mariadbd --no-defaults --verbose --help` on both bench images (path, host and id variables left out):

| Variable | 10.6.22 | 10.11.14 | Effect here |
|---|---|---|---|
| `explicit_defaults_for_timestamp` | OFF | **ON** (10.10) | A TIMESTAMP column without explicit `NULL`/`DEFAULT` is now nullable, default NULL, no auto-update. A dump states them, so production's schema is identical after the move. (Corrected in the port: B44 never ran; a fresh database replays V2/V3, whose `created_at` columns differ on 10.10+, as does V77's `account_token.expires_at`. V86 fixes them; see the port section.) **New migrations must keep stating them.** |
| `optimizer_prune_level` | 1 | **2** (+ `optimizer_extra_pruning_depth` = 8) | More aggressive join-order pruning for many-table joins. Our queries join at most three tables; no plan change expected. The benchmark checks it. |
| `innodb_prefix_index_cluster_optimization` | OFF | ON | Avoids clustered-index lookups for prefix-index reads; we have no prefix indexes on hot paths. |
| `innodb_log_write_ahead_size` | 8192 | 512 | Part of the 10.8 redo log rewrite (below). |
| `innodb_buffer_pool_chunk_size` | 128M | 0 (auto) | Buffer pool resizing granularity; with 256M no difference. |
| New: `innodb_buffer_pool_size_max`, `innodb_buffer_pool_size_auto_min` | – | 0 | Buffer pool resizing / shrinking under memory pressure. Inactive at these values; worth a look for the shared VPS, not needed. |
| New: `innodb_alter_copy_bulk` | – | ON | `ALTER ... ALGORITHM=COPY` builds the new table in bulk. Would have sped up V55.1's InnoDB conversion; that runs on the old server, before the move. |

Unchanged: `optimizer_switch` (the same flags in both), `histogram_type` (`DOUBLE_PREC_HB`; JSON histograms exist since 10.8 but aren't the default), `use_stat_tables`, `optimizer_use_condition_selectivity` = 4, `innodb_flush_method` = O_DIRECT, `innodb_log_file_size` = 96M, change buffering off. Ubuntu's `/etc/mysql` files in 24.04 differ from 22.04's only in the `[mariadb-10.11]` section name (production's copies also lack `bind-address = 127.0.0.1`).

The cost-based optimizer is the same generation as 10.6: the rewritten cost model is MariaDB 11.0. So 10.6 → 10.11 carries little risk of plans changing; a later move to 11.4 would be the one to benchmark plan by plan.

## V61: the gallery index with `rate` descending

(The original branch's design. Ported as V85 on `vote`, without the refusal on 10.6; see the port section.)

**Before.** V48 created `(jury_id, round_id, rate, monument_id, page_id)` for the gallery, but on 10.6 a mixed-direction `ORDER BY` can't be read from an ascending index, and 10.6 parses `DESC` in an index definition and ignores it. Each gallery page sorted all of the juror's rows of the round (~19k on the Gatling fixture). The deferred join (`ImageDbNew.deferredJoinPage`, commit 617dc75) limits that sort to narrow index entries (127 ms → 13 ms on the fixture), but the sort remains.

**V61.** `ALTER TABLE selection ADD INDEX idx_selection_jury_round_ratedesc_mon_page (jury_id, round_id, rate DESC, monument_id, page_id), DROP INDEX idx_selection_jury_round_rate_mon_page, ALGORITHM = INPLACE, LOCK = NONE`. The index has the same columns, so the gallery, its count, the region filter and the jurors' rate stats keep their access paths; only the order of `rate` within a juror's round flips. The page is then read from the index in order: with `LIMIT 15 OFFSET n` it reads n + 15 index entries instead of sorting the whole round. No query changes: the deferred join stays, because deep pages still read n entries, which is far cheaper index-only than with a full-row lookup for each.

**Guard.** On a server before 10.8, V61 stops with `V61 needs MariaDB 10.8 or later for descending index keys` before any DDL. Checked with the real ZIP on the 22.04 / 10.6.23 image. Without the guard, 10.6 would create the index ascending without a word, and a dump of it would carry the ascending index to 10.11, where Flyway would never run V61 again.

**Tests.** `SelectionGalleryIndexSpec` checks the index's column order and directions (`information_schema.STATISTICS.COLLATION` = `D` for `rate`), and that a gallery page over it needs no filesort and comes back in the gallery's order.

## Moving production

(The original branch's plan. In the port, V85 runs on 10.6 as a no-op and needs the re-run after the move; see the port section's pre-deploy items.)

1. Deploy the current release (V60) on the old server as planned (`docs/deployment.md`); V55.1's InnoDB conversion happens there.
2. Build the 24.04 server (`wlxjury-infra`, which still targets 22.04: `tests/Dockerfile`, the README, the inventory comment). MariaDB settings as now: the package files, the slow log, `innodb_buffer_pool_size = 256M`.
3. Move the database with `mariadb-dump --databases wlxjury` from 10.6 and restore it into 10.11. A dump of the application database only needs no `mariadb-upgrade`; the accounts come from the playbook. (An in-place datadir upgrade also works after a clean shutdown: the bench does exactly that, with `mariadb-upgrade`.)
4. Only then deploy this branch: V61 runs on 10.11 (online; it builds one secondary index: 10.9 s on the snapshot's 3.07M selection rows).

**Do not deploy this branch to the 22.04 server:** startup stops at V61, leaving a failed V61 row in `flyway_schema_history` that needs `flyway repair` (or the release tool's restore) before the old release starts again.

**V61 (B against C): less work for the galleries, no measurable cost.**
- The region gallery reads 35% fewer buffer-pool pages and its p95 drops from 31 to 23 ms: the region filter (`monument_id LIKE 'XX%'`) is applied to index entries read in page order, stopping at the page's end instead of collecting all of the juror's matching rows for a sort.

**Not changed by either:** every gallery page created one on-disk temporary table (`Created_tmp_disk_tables` = 1400 for 1400 pages, in all four runs). The slow log with `log_slow_filter = tmp_table_on_disk` and `long_query_time = 0` showed it was the gallery page itself: the deferred join's outer `ORDER BY rate DESC, s.monument_id, s.page_id` names columns of the second table, so MariaDB copied the joined rows, `images.description` (MEDIUMTEXT) included, into an on-disk temporary table (~2.1 MB for 15 rows) before sorting them. Fixed after these runs: the inner query also returns the order columns and the outer query sorts by them (`ORDER BY k.o0 DESC, k.o1, k.o2`), a filesort of k's 15 rows before the join with no temporary table. On the snapshot: identical rows, 1 temporary table instead of 2, none on disk, 500 runs 1056/1019 → 865/800 ms. Same on 10.6.
