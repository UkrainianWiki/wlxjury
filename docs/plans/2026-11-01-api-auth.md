# Serve the REST API with authentication: session for the SPA, personal tokens for tools

Status: implemented (see Results). Branch `ukwikidev/api-auth` from `ukwikidev/theme-modes`
at `cb103b24`, worktree `C:/scala/wlxjury-api`.

## Why

`app/api/Api.scala` defines four Tapir endpoints (contests: create, get, update, list) with
Swagger UI. It runs through the Pekko HTTP interpreter, which nothing serves: the app runs on
Play's Netty server. The endpoints have no authentication (CLAUDE.md, "REST API"). The API is
meant for a future SPA and for command-line tools, so it gets two ways in:

- **SPA:** the existing Play session cookie, with the `Csrf-Token` header on writes, as the
  gallery votes do today.
- **Command-line tools:** personal API tokens, `Authorization: Bearer <token>`.

Montage, for comparison, has only a signed session cookie for its Vue SPA and no CSRF check.
Its command-line tool talks to the database directly, not through the API. We want tools that
organisers run on their own machines, so tokens are needed.

## Decisions (the user's, 2026-11-01)

1. Both mechanisms: the session cookie for the browser, personal tokens for tools.
2. Tokens, version 1: a name, an optional expiry, `last_used_at`, revocation. No scopes: a
   token acts as its user, with that user's memberships and roles, through the same
   authorization code as a session.
3. The contest endpoints are root-only, as the contest pages are
   (`ContestController.list` / `saveContest` / `importContests`:
   `rolePermission(Set(User.ROOT_ROLE))`).
4. Swagger UI and the OpenAPI document are public at `/api/docs`. They hold no data.

## Design

### Serving

- Use Tapir's Play server interpreter (the artifact for Play 3.0 at Tapir 1.11.15, checked
  in `target/dep-sources` or the artifact list, not assumed) and mount it from `conf/routes`
  (`-> /api api.ApiRouter`, or the Tapir router's documented way). Requests then go through
  all of Play's filters (CSRF, security headers, CSP, allowed hosts once that is on) and the
  same error handler.
- Remove the Pekko HTTP interpreter (`tapir-pekko-http-server`). Remove `pekko-http-play-json`
  and `pekko-http-testkit` too if nothing else uses them. `pekko-http` itself stays if
  `GalleryController` or `LocalImageCacheService` still need it; check by compiling.
- Endpoints: keep `/api/contests…`. Blocking JDBC work runs on `blocking-dispatcher`, as now.

### Who is calling

One function resolves the caller for every API request:

1. An `Authorization` header that is present must be `Bearer <token>`, and the token must be
   valid (exists, not revoked, not expired). Otherwise the answer is 401. If the header is
   present, the session cookie is ignored, so a request never mixes the two.
2. Otherwise, the session user as `Secured.userFromRequest` gives it, in the session's
   current contest.
3. Otherwise, 401.

A token's user is loaded the same way a session user is, so `hasAnyRole`, memberships and
root work unchanged. Tokens are accepted only under `/api/`, never on the page routes, the
votes or `/theme`.

### Errors (JSON)

- 401: `{"error": "unauthorized"}` with `WWW-Authenticate: Bearer`.
- 403: `{"error": "forbidden", "reference": …}`, logged through `Secured.logDenial`, the
  same line on `security.authz` as `onUnAuthorizedJson`, plus whether the caller came in by
  session or by token (the token's id, never its value).
- Decode failures (a bad JSON body, a bad path id): 400 `{"error": "bad_request"}` without
  echoing the input (CLAUDE.md "Errors"). Set Tapir's decode failure handler for this.
- Not found: 404 `{"error": "not_found"}`.
- A token that is invalid, expired or revoked: log it at WARN with its id or prefix only.

### CSRF

- Session-authenticated writes (POST, PUT, DELETE) must carry the `Csrf-Token` header, as
  Play's CSRF filter requires for gallery votes.
- Bearer requests carry no cookie and need no CSRF token. Check how Play 3.0.7's CSRF filter
  decides this (`play.filters.csrf.header.*`, read in `target/dep-sources`) and configure it
  narrowly, for example by bypassing only when an `Authorization` header is present and there
  is no session cookie. Never bypass it for a request that carries the session cookie.
- A refused token goes through `CsrfErrorHandler` (JSON `{error: "csrf", reference}`), as
  today.

### Tokens

- **Migration V75** (the next number; V74 is the last on this branch):
  `api_token(id BIGINT PK AUTO_INCREMENT, user_id BIGINT NOT NULL FK users(id) ON DELETE
  CASCADE, name VARCHAR(100) NOT NULL, token_hash CHAR(64) NOT NULL UNIQUE,
  prefix VARCHAR(16) NOT NULL, created_at TIMESTAMP(3) NOT NULL, expires_at TIMESTAMP(3) NULL,
  last_used_at TIMESTAMP(3) NULL, revoked_at TIMESTAMP(3) NULL)`, InnoDB, utf8mb4, MariaDB 10.6
  syntax (production is on 10.6; nothing that needs 10.8 or later). Index `user_id`.
- **Format:** `wlxj_` followed by 32 random bytes from `SecureRandom`, base64url without
  padding. The prefix (`wlxj_` plus the first 6 characters) is stored to name the token in
  lists and logs, and so that secret scanners recognise it. Only the SHA-256 hash of the
  whole token is stored. A lookup hashes the presented token and finds it by the hash, which
  is the unique key.
- **Shown once,** on the page right after creation, with a copy button. It is never shown
  again, and never in a flash cookie, a log line or a URL.
- **`last_used_at`** is updated at most once a minute per token.
- **Management** is on the user's own profile page (`editUser`, own profile only), in an
  "API tokens" card:
  - the list: name, prefix, created, last used, expiry, and a Revoke button;
  - a create form: a name, and an expiry of 30 days, 90 days, a year or never (default 90
    days).

  Create and revoke are POST forms with `csrfField`. Only a session can create a token: a
  token can't create or revoke tokens, so a leaked token can't extend itself. A user can
  revoke only their own tokens. Root revoking other users' tokens is left for later.
- **Messages** in en, fr, uk and ru (`MessagesCompletenessSpec`).

### OpenAPI

Declare both security schemes, a bearer token and the session cookie, on the contest
endpoints, so Swagger UI shows them. `/api/docs` must render under the production CSP
(`ui-shots.py --csp` or a request check). If Swagger UI needs anything the CSP doesn't allow,
report it rather than widening the CSP.

### Docs

- CLAUDE.md "REST API": served, how auth works, root-only contests, tokens.
- A short "API" section in `docs/deployment.md`, or in a new `docs/api.md`, with a `curl`
  example using a token.

## Tests (negative cases first)

- Contest endpoints: no credentials → 401 with `WWW-Authenticate`. A juror's session → 403.
  An admin of a contest who isn't root → 403, for each of the four endpoints. Root's session
  → 200. Root's token → 200.
- A revoked, an expired, a malformed or an unknown token → 401, and nothing is changed. An
  `Authorization: Basic …` header → 401.
- A bearer header together with a root session cookie and a bad token → 401: the cookie
  doesn't rescue the request.
- CSRF, with `controllers.CsrfTestApp.withCsrfApp`: a session POST/PUT without `Csrf-Token`
  → 403 (csrf). The same with the header → it passes. A bearer POST without a cookie and
  without a CSRF token → it passes. A bearer POST that also carries the session cookie,
  without a CSRF token → refused.
- A token on a page route (e.g. `/admin/rounds`, `/rate/...`, `/theme`) doesn't sign in:
  the same answer as no credentials.
- Token management:
  - create needs a session and the CSRF token;
  - a token can't create or revoke;
  - another user's token can't be revoked (404, nothing changed);
  - the DB holds only the hash (the plain token appears in no column);
  - the plain token appears only in the response that creates it, not on reload;
  - `last_used_at` is set by a use.
- Logs: the token value never appears in a captured log line. Denials log the reference and
  the token id.
- Errors: a malformed JSON body → 400 `bad_request` without the body's text; an unknown
  contest → 404 JSON.
- `/api/docs` and the OpenAPI JSON → 200 without credentials.
- `MigrationNamingSpec`, and V75 on a fresh DB through the shared Testcontainer.
- Replace `test/api/ApiSpec` (Pekko route testkit) with a Play test.

## Invariants (every reviewer checks)

- No path accepts a token outside `/api/`. No token value is logged, flashed, put in a URL or
  stored in plain text.
- Session writes always need CSRF. The only bypass is a bearer request without the session
  cookie.
- Authorization goes through the existing `Secured` permissions and `User` role checks. There
  is no second role model.
- Errors are JSON without request or exception text. Denials are logged with a reference.
- The existing page routes, votes, sign-in and the theme switch behave as before.

## Results

### What changed

- **Serving:** `tapir-play-server` 1.11.15 (built for Play 3.0.6; `play-pekko-http-server`
  excluded, Netty stays) replaces `tapir-pekko-http-server`; `pekko-http-play-json` and
  `pekko-http-testkit` are gone, `pekko-http` stays (GalleryController, LocalImageCacheService).
  `-> /api api.ApiRouter` (a `SimpleRouter`, so the endpoints' paths start below `/api`).
  Any other `/api` path is a JSON 404 (a catch-all endpoint).
- **Who calls:** `api.ApiAuth` (`caller`, `authorize`) from the raw Play request, not Tapir
  auth inputs (Tapir's cookie parser rejects some cookie values, and a non-Bearer header must
  not fall back to the session). Root-only through `Secured.checked` (new, shared with the
  action builders), `Secured.sessionUserOf` (shared by `userFromRequest`).
  `Secured.logDenial` / `denialLogLine` take extra trusted fields (`auth=session`,
  `auth=token tokenId=…`). Errors: `api.ApiFailure`, a decode failure handler that keeps only
  the status, and an exception handler (500 with a logged reference).
- **CSRF:** `modules.CsrfModule` replaces `play.filters.csrf.CSRFModule` (disabled in both
  configs) with the same bindings and a `CSRFConfig` whose `shouldProtect` is the configured
  one and not `ApiAuth.bearerWithoutSession` (path under `/api/`, exactly one
  `Authorization: Bearer …`, no session cookie by the configured name, empty session). The
  filter class is unchanged, so the test config and `CsrfTestApp` work as before.
- **Tokens:** V75 `api_token` (as planned; `user_id` is `BIGINT UNSIGNED` like `users.id`,
  `created_at` defaults to `CURRENT_TIMESTAMP(3)`), `ApiTokenJdbc` (times by the DB clock,
  `expired` computed in SQL), `services.ApiTokenService`. `last_used_at`: a conditional
  `UPDATE` per use that writes at most once a minute.
- **Profile:** `apiTokens.scala.html` card on the own profile only (`UserController.editUser`,
  `createApiToken`, `revokeApiToken`; `controllers.ApiTokensCard`), `copy-field.js` (Copy
  button) with a Jest test, 26 message keys in en/fr/uk/ru.
- **OpenAPI:** both schemes (`bearerToken`, `sessionCookie`) added through
  `customiseDocsModel`, as top-level security; the server URL is `/api`.
- **Docs:** CLAUDE.md "REST API", new `docs/api.md` (curl with a token, errors, operator notes).
- **Tests:** `test/api/ApiSpec` (replaced: Play router + filters), `controllers.ApiTokenPageSpec`,
  `db.scalikejdbc.ApiTokenJdbcSpec` (V75 schema, hash-only storage, expiry, refusals,
  once-a-minute use, own-only revoke); `views.AppRoutes` now builds the included API router
  (its null argument broke `router.Routes`' constructor); `api_token` is truncated with the
  other tables.
