## Method and rules applied

- **Cuts:** at every `--no-ff` batch merge and at every theme change inside runs of direct
  commits. Each PR tip is a real first-parent tree.
- **Commits inside a PR:**
  - sub-theme cuts, also at first-parent points;
  - when the PR changes 150 or more lines of docs, a separate trailing **docs commit**, so the
    code commits come without the plan and result docs.

  The non-docs commits' trees are first-parent trees with the PR's docs changes left out.
  Tests stay with their code, so each commit compiles as it did then. The docs split was not
  used in four PRs:
  - PR 10 and PR 15 already have 4 sub-theme commits;
  - PR 40 interleaves docs and code;
  - PR 06 is data.
- **Size rules:** about 3–5k lines of code + tests at most, where the history allows. Tiny
  neighbours of the same theme are merged (B1 with B2, B6 with B8, the agent-check tooling with
  region improvements, the shared filter test app with S7, the region-stat query and the
  prod-dump script into the DB-index PR). The Gatling CSVs are a **data-only PR (06)**. Docs-only
  "Record …" commits stay with the batch they record. Plans and decisions without code (#552–#554,
  #557–#567) ride with S1, as separate commits.
- **Migration order:** checked at every PR tip. The only out-of-order number in the history is
  **V55.1** (#261, added after V56–V59). So PR 15 runs from V56 (#217) through V55.1 (#261),
  with perf-memory, background jobs and the InnoDB conversion as 4 commits. Cutting anywhere
  inside it would give a tip where V55.1 lands below V59, which Flyway refuses on an upgraded
  database without `outOfOrder`.
- **V77–V80:** they arrive in merge order S2 (V77), C1 (V78), S5/S10 (V79), S3 (V80), so each of
  those batches is its own PR.
- **Migrations edited after they were added** must not be split across PR tips: a dev database
  would see a checksum or description change. Every pair is kept inside one PR: V46 (#123,
  edited #169), V48 (#140/#143), V53 (#198–#200), V56 (#217/#220), V61 (#287/#288), V63
  (#290–#295), V68 (#344/#346), V72 (#452/#460) and V73 (#470/#474).
- **Two harmless exceptions:**
  - `V45a`–`V45g` (#127, removed at #211) sit at PR tips 10–13. Their names are invalid
    Flyway versions, so Flyway never applied them (commit "Create the V45 performance indexes
    Flyway never applied").
  - `B44` (added #87, edited #169, removed in PR 51). Flyway 9.16.3 has no `B` migrations and
    never applied it.

`--onto` works because each PR tip has exactly the same tree as its followups original, so
every replayed patch meets the same context. This holds whatever merge style GitHub uses.

**Merging the stack:** merge in order. A fast-forward of `master` to each approved tip keeps
the SHAs, and GitHub marks the PR merged. With "Rebase and merge", retarget the next PR and
`git rebase --onto origin/master <old previous tip>`; there are no conflicts because the trees
are identical. "Squash and merge" is fine for the 1-commit PRs, but it would collapse the
curated code/docs split of the others.

## Workflow from here (implementer → review → fixes → merge)

- **`master` is the trunk.** One short-lived branch and **one PR per batch**, cut from current
  `master`. No long-lived integration branch with `--no-ff` merges, and no merging the trunk
  into batches (rebase instead).
- **Curate at merge:** the orchestrator rewrites the batch into 1–3 commits (migration + code
  with its tests; docs and plan results), or squash-merges. GitHub keeps the originals in
  `refs/pull/<n>/head`.
- **No direct "Record …" commits on the trunk.** Results go in the batch's docs commit.
  Roadmap and decision notes go in a periodic small docs PR. 562 of the 605 first-parent
  commits were direct.
- **Migration numbers:** assign them at merge. Add a guard that a PR's new `V` numbers are above
  `master`'s maximum, and that no merged migration is edited (this history has 9 edits and one
  out-of-order V55.1).
- **Releases:** `release/<version>` branches for production. The first is at `f3f2c736` (prod +
  hotfix); hotfixes go there and are then picked to master.
- **Size:** aim for about 3–5k lines of code and tests per PR. Split a batch before
  implementation if its plan predicts more. Of the oversized PRs here, two are single merges
  that were never split.
- **Per-PR gate:** record the full-suite commit and log in the PR description. Avoid long
  stretches of tips with no recorded run, like PRs 01–26.
- **Work in progress:** at most 2–3 batches open at once.
