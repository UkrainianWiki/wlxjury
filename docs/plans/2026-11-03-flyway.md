# Flyway batch: why newer Flyway broke fresh databases, own runner, upgrade to 13.12.0 (2026-11-03)

Branch `ukwikidev/flyway-baseline` (worktree `C:/scala/wlxjury-flyway`, from `ukwikidev/followups`
`82cfba45`). Roadmap item "After P0: the Flyway batch" (`docs/plans/2026-11-02-roadmap.md`).

## 1. The cause: B44 was never applied, and newer Flyway applies it

The hypothesis was that baseline migrations (`B__`) became a Teams-only feature after 9.16.3.
The sources say the opposite.

- **Flyway 9.16.3 has no baseline migrations at all.** Its jar (`flyway-core-9.16.3.jar`, 521
  entries) has no class for them; the only `ResourceTypeProvider` registered
  (`META-INF/services/org.flywaydb.core.extensibility.Plugin`) is
  `org.flywaydb.core.internal.resource.CoreResourceTypeProvider`, whose `getPrefixTypePairs`
  returns the `V` (`MIGRATION`), `R` (`REPEATABLE_MIGRATION`) and callback prefixes only, and
  `CompositeMigrationResolver` adds no resolver for `B`. `ResourceNameParser.populatePrefixes`
  collects exactly those prefixes, so `B44__Baseline.sql` never matched: 9.16.3 skipped it
  silently (validateMigrationNaming is off) and built every empty database — the test suite's,
  the Gatling fixture's, any fresh install — by running V1..V82. B44 never ran anywhere, and no
  history (production's included) can have a row for it.
- **Baseline migrations came to Flyway Community in 9.21.0** (the class
  `org.flywaydb.core.api.migration.baseline.BaselineMigrationResolver` is in the 9.21.0 and
  9.22.x jars, not in 9.19.4, 9.20.0 or 9.20.1) and are still Community in 13.12.0, registered as
  plugins (`BaselineMigrationResolver`, `BaselineResourceTypeProvider`,
  `BaselineMigrationConfigurationExtension` with prefix `B`, `BaselineAppliedMigration`). On an
  empty database `MigrationInfoServiceImpl.getPendingResolvedVersionedMigrations` sets
  `context.pendingBaseline` to the newest `B` version (44); `ResolvedMigration.getState` then
  gives V1..V43 `BELOW_BASELINE` and V44 `BASELINE_IGNORED`, and
  `BaselineResolvedMigration.getState` makes B44 `PENDING` (it becomes `IGNORED` once anything
  is applied, `migrationsAppliedOrBaselineExists`). So 9.22.3 ran B44 and then V46 onward.
- **B44 didn't match V1..V44.** Commit `80307e51` ("fix migration", 2026-04-14) edited it by hand:
  `monument.id` `NOT NULL` with a `PRIMARY KEY`, instead of the nullable column with
  `KEY monument_id_index` that V6/V7 create. V51 (`DROP INDEX monument_id_index`) then failed on
  B44 under 9.22.3: "Can't DROP INDEX monument_id_index" (the memory note's 2026-10-19 failure).
  The same commit took the monument key promotion out of V46 (`ALTER TABLE monument MODIFY id
  … NOT NULL`, `ADD PRIMARY KEY (id)`, `DROP INDEX monument_id_index`), moving it into B44, which
  9.16.3 never read: V46's checksum changed, and since then a fresh database's `monument` has
  no primary key (V51 replaces `monument_id_index` with the unique `monument_id_unique`). A
  database that applied V46 before 2026-04-14 would have the old V46 checksum and fail
  validation; production doesn't (it validates on every start and started on `f9c31ce5`:
  section 5).

What earlier notes said about "the B44 baseline" (the test suite running on it, "B44 alone
3.8–5.4 s", `ConvertToInnoDbMigrationSpec`'s "V65 a no-op on the B44 baseline") described a
replay from V1.

## 2. What changed instead of a baseline mechanism

The approved task 2 (run B44's SQL, record a baseline at 44, migrate V45 onward) would have
reproduced the V51 failure: B44's content is not the V1..V44 schema. Making it so means cutting a
new baseline, which the user put after P1. So nothing builds databases from a baseline now, and
empty databases are built exactly as 9.16.3 built them, V1 onward:

- **`B44__Baseline.sql` removed** from `conf/db/migration/default` (it was never applied; git keeps
  it). `MigrationNamingSpec` "be a versioned migration, no baseline script" refuses a `B` file
  there: with Flyway 9.21+ any `B` file decides how every empty database is built.
- **`SchemaBaselineSpec`** (`-Dgenerate.baseline=true`) dumps the migrated schema to
  `target/schema-baseline.sql` instead of writing `B44__Baseline.sql` into the migrations.
- **For the later baseline cut** (after P1): Flyway Community's own `B<n>__` works (see above:
  applied only to an empty schema, `IGNORED` on a database with history, and validation skips an
  ignored baseline, `MigrationInfoImpl.validate`: `!resolvedMigration.getType().isBaseline()`).
  It must equal V1..V<n> (a schema diff like `FlywayUpgradeSpec`'s, plus the seeded rows), and
  the specs that build a database to an older target (`ConvertToInnoDbMigrationSpec`'s
  `flywayTo(…, "64")`) need V files below it kept or a different start.

## 3. Flyway run by the app: `db.Migrations` (no flyway-play)

flyway-play is stale (9.1.0, April 2024, built against flyway-core 9.16.0) and doesn't work with
Flyway 10+: its `Flyways` calls `FluentConfiguration.cleanOnValidationError`, which Flyway 13.12.0
no longer has (`production.conf` sets the key, so the start would fail with `NoSuchMethodError`),
and it builds `org.flywaydb.core.internal.jdbc.DriverDataSource` itself.

`app/db/Migrations.scala` is the one place that configures and runs Flyway:

- `Migrations.Settings.fromConfig` reads the same `db.default.migration.*` keys flyway-play read
  (`auto`, `validateOnMigrate`, `validateOnStart`, `initOnMigrate` → `baselineOnMigrate`,
  `outOfOrder`, `ignoreMigrationPatterns` (none by default, as flyway-play set), `cleanDisabled`,
  and `cleanOnValidationError`, accepted only as false). An unknown key fails the start.
- `Migrations.flyway/migrate(url, user, password, settings)`: Flyway's own connections (as
  flyway-play's), classpath `db/migration/default`, optional `target`.
- `Migrations.onStart(config, mode)`, run by the eager `modules.DatabaseMigrations`
  (`modules.DatabaseMigrationsModule`, enabled where `org.flywaydb.play.PlayModule` was, in
  `conf/application.conf` and `test/resources/application.conf`): Test always
  migrates; Prod and Dev migrate with `auto`, otherwise refuse to start while a migration is
  pending (`Migrations.PendingMigrations`, versions and scripts only), then validate if
  `validateOnStart`. **Dev changed:** flyway-play's "apply" page is gone; `sbt run` on a database
  with pending migrations needs `-Ddb.default.migration.auto=true` (CLAUDE.md).
- **Order:** the module's place orders nothing. Guice builds an eager provider binding
  (`bind(JobScheduler).toProvider(JobSchedulerProvider).asEagerSingleton()`) before an earlier
  module's eager singleton, and in Prod (Guice's PRODUCTION stage) Play builds the router, its
  controllers and so the scheduler early. `modules.MigrationOrderSpec` showed it before the fix
  (Prod mode, background jobs: the scheduler's provider was built at provision event 38, the
  scheduler at 66, the password timer at 434, the migrations ended at 525): the scheduler could
  take over a requeued distribution on a half-migrated schema (V82's renames, for one). What
  uses the database at the start now takes `DatabaseMigrations` as a constructor dependency, so
  Guice builds it only after the migrations ran: `JobSchedulerProvider` (which starts the
  scheduler) and `LegacyPasswordRetirementTask` (its timer). The other singletons read the
  database only on a request (`SessionUpgradeWindow`, `ReadinessCheck`) or touch only files
  (`LocalImageCacheService`'s registry). `MigrationOrderSpec` checks the order of Guice's
  provision events in a Prod-mode app and that both constructors depend on `DatabaseMigrations`;
  a new eager database user must do the same.
- Used by `SharedTestDb`, `ConvertToInnoDbMigrationSpec.flywayTo` (target versions) and
  `FlywayUpgradeSpec`; the Gatling fixture, `SharedPlayApp`/`PlayTestDb` and every test app go
  through the module. `GatlingDbCache.cacheKey` hashes the migration files, so removing B44 makes
  one fresh fixture build; the fixture's rows don't change (`FixtureVersion` unchanged).

## 4. The version: Flyway 13.12.0

Newest on Maven Central on 2026-11-03: flyway-core / flyway-mysql **13.12.0** (jar dated
2026-10-30). Checked from its sources (`flyway-core-13.12.0-sources.jar`,
`flyway-mysql-13.12.0-sources.jar`):

- **Java:** class files major version 61 (`org/flywaydb/core/Flyway.class`): Java 17, as ours.
- **MariaDB:** `org.flywaydb.database.mysql.mariadb.MariaDBDatabase.ensureSupported` calls
  `ensureDatabaseIsRecentEnough("5.1")` (refuses older), then
  `ensureDatabaseNotOlderThanOtherwiseRecommendUpgradeToFlywayEdition("10.3", Tier.PREMIUM, …)`,
  which below 10.3 only logs at info ("outside of Redgate community support",
  `Database.ensureDatabaseNotOlderThanOtherwiseRecommendUpgradeToFlywayEdition`), and
  `recommendFlywayUpgradeIfNecessary("12.3")`, a warning above 12.3. MariaDB 10.6 and 10.11: no
  refusal and no warning (9.16.3 warns on 10.11, "latest supported 10.10"). Checked on 10.11.14
  (below).
- **Community, no network:** the only `FlywayTelemetryManager` registered is
  `NullFlywayTelemetryManager`; "native connectors" need a `NativeConnectorsSupport` plugin
  that neither jar has (`NativeConnectorsModeUtils.canUseNativeConnectors`).
- **History compatible:** the MySQL/MariaDB history table DDL (`MySQLDatabase.getRawCreateScript`)
  is the same as 9.16.3's; `ChecksumCalculator` computes a single file's checksum as before (the
  CRC32 of its lines, BOM stripped; only a script with referenced scripts differs);
  `MigrationInfoImpl.validate` checks the same states, type, checksum and description;
  `CoreMigrationType` lost only the deprecated `SCRIPT_BASELINE`, which no 9.16.3 history has.
- **flyway-play:** no release for it (above): replaced by `db.Migrations`.
- **Why not 13.11.1:** the reviewer diffed 13.11.1 and 13.12.0: the same code except H2's
  recommended version, and 13.12.0 makes `jackson-annotations` optional, so it doesn't pull a
  Jackson newer than Play's 2.14.3. 13.12.0 stays, though it is only days old.

**MariaDB 10.11.14** (`-Dwlxjury.test.mariadb-image=mariadb:10.11.14`, Flyway 13.12.0): every
migration spec passes, a fresh database's history is identical to 10.6's, no Flyway warning; the
two schema comparisons against databases restored from 10.6 dumps fail, on two columns only:
`round.created_at` (V3: `timestamp NOT NULL` without a default on 10.11, `DEFAULT
current_timestamp() ON UPDATE current_timestamp()` on 10.6) and `users.created_at` (V2: `NULL
DEFAULT current_timestamp()` on 10.11, `NOT NULL DEFAULT current_timestamp()` on 10.6). That is
MariaDB, not Flyway: `explicit_defaults_for_timestamp` is ON by default from 10.10, so a

its 10.6 definitions; a database created fresh on 10.11 differs (an `INSERT` into `round` without
`created_at` would fail there in strict mode). For `ukwikidev/mariadb-10.11`: either set
`explicit_defaults_for_timestamp=OFF` on the new server or add a migration that states those two
columns' attributes explicitly; `FlywayUpgradeSpec` with the image property shows it.

## 5. Production: what the first start with Flyway 13.12.0 does, pre-deploy checks, rollback

Production (schema 70, history written by 9.16.3 and earlier) starts with `production.conf`'s
`db.default.migration` block (`auto = true`, `validateOnMigrate = true`, `initOnMigrate = false`,
`cleanDisabled = true`, `cleanOnValidationError = false`, `ignoreMigrationPatterns = []`):

1. `db.Migrations` reads the block; **an unknown key there fails the start** (before Flyway
   connects). The installed `/etc/wlxjury-runtime/production.conf` must have only these keys in
   the block (and no `-Ddb.default.migration.*` in `/etc/default/wlxjury` other than these).
   Read-only checks on the server. They print the block and key names only, no values; never
   grep `runtime.env` (the service's EnvironmentFile, it holds secrets) for anything but these
   key names:

   ```bash
   sudo sed -n '/db.default.migration/,/}/p' /etc/wlxjury-runtime/production.conf
   # dotted keys outside the block too, with line numbers
   sudo grep -no 'db\.default\.migration[.A-Za-z]*' /etc/wlxjury-runtime/production.conf
   sudo grep -o 'db\.default\.migration\.[A-Za-z]*' /etc/default/wlxjury
   sudo grep -o 'db\.default\.migration\.[A-Za-z]*' /etc/wlxjury-runtime/runtime.env
   systemctl cat wlxjury | grep -o 'db\.default\.migration\.[A-Za-z]*'
   ```

   Expected: the block with `auto`, `initOnMigrate`, `validateOnMigrate`, `cleanDisabled`,
   `cleanOnValidationError`, `ignoreMigrationPatterns` only; the `-no` grep shows only the
   block's opening line (or those keys, dotted); the last three print nothing (or only those
   keys).
2. Flyway validates the history against the files. It passes if production's rows for V1..V70
   match the files, as they do for 9.16.3 today: V1..V70 are byte-identical between `f9c31ce5`
   (main) and this branch (`git diff f9c31ce5..HEAD -- conf/db/migration/default` touches only
   V71..V82 and B44), and 13.12.0 computes the same checksums as 9.16.3 (`FlywayUpgradeSpec`: the
   V70 fixture's 9.16.3 rows validate unchanged; the fresh histories are identical). B44 was
   never in any history (9.16.3 couldn't apply it). Nothing in the history table is changed,
   repaired or added before migrating; no baseline row is written (`initOnMigrate = false`, and
   the schema has a history table anyway).
3. It applies the pending migrations (V71 onward) as `SQL` rows, as 9.16.3 would.

Pre-deploy (on the rehearsal copy and on production, read-only):

- `SELECT DISTINCT type FROM flyway_schema_history;` — expect `SQL` (maybe `BASELINE`,
  `SCHEMA` or `DELETE` (a `repair` of a removed migration), all still known to 13.12.0).
  `SCRIPT_BASELINE`, `SQL_BASELINE` or a `B…` script would be unexpected: stop and look.
- Production is already cleared of the V46 checksum risk (section 1): 9.16.3's `migrate`
  validates the history first on every start (`Flyway.migrate`, `Flyway.java:141` in 9.16.3,
  with production's `validateOnMigrate = true`), and production started on `f9c31ce5`, whose
  V1..V70 are byte-identical to this branch's. The comparison below is an optional cross-check
  of production's checksums against 9.16.3's fresh history (run the query by whoever can read
  production's database, on the database `${WLXJURY_DB}` names; the repo file holds no secrets):

  ```bash
  mariadb -N -B -e "SELECT version, checksum FROM flyway_schema_history
                    WHERE type = 'SQL' AND success = 1" "$WLXJURY_DB" | sort -V > prod-history.tsv
  awk -F' [|] ' '{print $2 "\t" $6}' test/resources/db/flyway-9.16.3-fresh-history.txt \
    | sort -V > repo-history.tsv
  grep -Fxv -f repo-history.tsv prod-history.tsv   # expect no output
  wc -l < prod-history.tsv                          # 70 at V70 (no V45; V55.1 included)
  ```

  A line printed would be a migration production applied with other content than the file
  today; given the above none is expected. Deciding on a `repair` would be a separate,
  deliberate step, never automatic.
- `SELECT COUNT(*) FROM flyway_schema_history WHERE success = 0;` — 0 (as the readiness check).
- The rehearsal (`docs/deployment.md`) runs the release on a production copy: its log should show
  no validation error and the migrations from V71.

Rollback, as `scripts/deployment/wlxjury-release.sh` allows it. The history table keeps 9.16.3's
format, so the previous release (9.16.3 + flyway-play) reads it, but the tooling decides what
may run:

- `deploy` takes the backup (`backup-complete`) because this release has new migrations for
  production (V71 onward; without them it would skip the backup unless `--backup`), then marks
  `migration-may-start` **before** `systemctl start`, Flyway's first run.
- Up to `migration-may-start` (the checks, maintenance, the backup): nothing was migrated;
  start the app if it was stopped and `reopen` (`docs/deployment.md`).
- From `migration-may-start` on, `reopen` refuses the previous release ("a migration may have
  run: run wlxjury-release restore first") even if Flyway stopped at validation and changed
  nothing. The way back is `wlxjury-release restore OPERATION` (it imports the whole pre-deploy
  dump and switches the release back), then `reopen`: the outage of a full import.
- A forward fix stays possible without a restore when the candidate can be made ready: e.g. an
  unknown `db.default.migration` key (step 1) or another start failure before Flyway changed
  anything: fix the runtime config, `systemctl start wlxjury`, and `reopen` accepts the
  candidate once `/health/ready` answers.
- After `traffic-may-resume` a restore loses later writes (`--accept-data-loss`, deployment.md).
  Once migrated, the old release refuses the history anyway: it has migrations the old files
  lack (`ignoreMigrationPatterns = []`).
